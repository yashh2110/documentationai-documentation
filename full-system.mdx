## 1. System Overview

This system is an **AI-powered garment image processing pipeline** for an e-commerce platform. It takes raw product images and metadata as input and produces:

1. A structured set of \~44 product attributes (brand, category, fabric, colour, style tags, eBay category, etc.)

2. A retouch-ready enhancement prompt tailored to the specific garment

3. An enhanced, background-removed, colour-corrected product image stored in S3

The system is designed as three independent microservices that hand off data through a combination of:

- HTTP calls (synchronous)

- AWS SQS message queues (asynchronous)

- AWS S3 object storage (asynchronous shared state)

- AWS DynamoDB (job state management)

### The Three Services

| Service               | Folder               | Port | Runtime Model                    |
| --------------------- | -------------------- | ---- | -------------------------------- |
| **AI-Tagging**        | `AI-Tagging/`        | 9000 | HTTP API + background SQS worker |
| **Prompt-Gen**        | `Prompt-Gen/`        | 8000 | HTTP API only                    |
| **AI-Image-Enhancer** | `AI-Image-Enhancer/` | 9090 | HTTP API only                    |

### Data Flow Summary

```
E-commerce Platform → AI-Tagging API → [SQS Queue] → AI-Tagging Worker
                                                             │
                                                        Gemini AI
                                                             │
                                               AI-Tagging Worker → Prompt-Gen API
                                                             │          │
                                                             │     OpenAI / Gemini
                                                             │
                                          S3 (enhance-profiles/{job_id}-{orientation}.json)
                                                             │
                          AI-Image-Enhancer API ─────────────┘
                                    │
                          fal.ai → Background Removal API → S3 (enhanced image)
```

## 3. Responsibilities of Each Service

### AI-Tagging

**What it owns:**

- The job lifecycle state machine (pending → queued → processing → complete/error)

- All attribute extraction logic (Gemini 2-pass pipeline)

- Priority queue management

- The bridge to Prompt-Gen (calling it and assembling the result into an enhance profile)

- Writing enhance profiles to S3

**What it does NOT own:**

- Image enhancement (no fal.ai calls)

- Prompt generation logic (delegates to Prompt-Gen)

- Image enhancement execution (delegates to Image-Enhancer)

**Data it produces:**

- DynamoDB record with `state=complete` and full attribute JSON

- S3 objects: `prompts/{job_id}-front.json` and `prompts/{job_id}-back.json`

---

### Prompt-Gen

**What it owns:**

- The logic to generate a retouch instruction prompt from an image and garment description

- LLM backend selection and routing (OpenAI vs Gemini)

- Back-view vs front-view prompt differentiation

- Denim special handling

**What it does NOT own:**

- Any state, storage, or caching

- Anything about the job lifecycle

- Anything about image enhancement execution

**Data it produces:**

- A single string: the retouch prompt

---

### AI-Image-Enhancer

**What it owns:**

- The image enhancement execution pipeline

- Background removal integration

- fal.ai model invocation and result handling

- LAB colour correction

- Final S3 image upload

**What it does NOT own:**

- Attribute extraction (no Gemini attribute calls)

- Prompt generation (reads prompts from S3, doesn't generate them)

- Job state tracking (no DynamoDB)

**Data it produces:**

- Enhanced image file stored in S3

- Public S3 URL of the enhanced image

### Service Communication Topology

**AI-Tagging → Prompt-Gen** (synchronous HTTP call):

```
From: enhance_profile.py → build_enhance_profile()
To:   server.py → POST /generate-prompt
Auth: X-API-Key header (PROMPT_GEN_API_KEY)
Body: {image_url, orientation, item_type, fabric_type}
Response: {"prompt": "retouch instruction string"}
```

**Client → AI-Image-Enhancer** (synchronous HTTP call — not initiated by AI-Tagging):

```
From: client (independent trigger, not AI-Tagging)
To:   app.py → POST /image-enhance/v1/<model>
Auth: None
Body: {url, bucketName, filePath, prompt (S3 key), width, height, ...}
```

**Key architectural point:** AI-Tagging and AI-Image-Enhancer do **not** directly call each other. The handoff is through **S3** — AI-Tagging writes an enhance profile to S3, and the client is expected to then call AI-Image-Enhancer with the S3 path of that profile. This is a **shared-state async decoupling** pattern.

## 5. End-to-End Request Flows

### Flow 1: Standard Garment Processing (Full Pipeline)

```
Step 1 — Client submits garment job
  POST /garment-tagging/upload
  {uuid, image_url: [...], attribute: {brand, category, gender, material, studio}}
  
  → main_api.py writes DynamoDB: {job_id, state=pending, data=...}
  → main_api.py sends SQS message: {job_id, data}
  ← Returns: {status: true, data: {job_id, null_attributes}}

Step 2 — Client polls for job completion
  GET /garment-tagging/query?uuid=<job_id>
  ← Returns current state {state: pending|processing|complete|error}
  (Client repeats until state=complete or state=error)

Step 3 — Worker picks up job from SQS (asynchronous)
  worker.py SQS receive_message
  → DynamoDB: state=processing
  → Downloads images: image_url[1:-1] → image grid, image_url[0] → front, image_url[-1] → label
  → Pass 1: Gemini classify eBay Category
  → Pass 2: Gemini extract 44 attributes (category-specific valid values)
  → validate_response: strip hallucinations
  
  → [if PROMPT_GEN_URL set]
      → enhance_profile.build_enhance_profile(image_url[0], "front", ...)
          → POST Prompt-Gen /generate-prompt (front view)
          ← {"prompt": "front retouch instruction"}
      → enhance_profile.build_enhance_profile(image_url[1], "back", ...)
          → POST Prompt-Gen /generate-prompt (back view)  
          ← {"prompt": "back retouch instruction"}
      → Assemble: {prompt, lora_prompt, guidance_scale, guidance_scale_lora, loras, metadata}
      → S3.put_object: prompts/{job_id}-front.json
      → S3.put_object: prompts/{job_id}-back.json
  
  → DynamoDB: state=complete, result=json.dumps(final_output)
  → SQS.delete_message

Step 4 — Client retrieves completed attributes
  GET /garment-tagging/query?uuid=<job_id>
  ← Returns: full tag JSON with 44 attributes, measurements, description

Step 5 — Client triggers image enhancement (manual/orchestrated)
  POST /image-enhance/v1/flux-kontext-pro
  {
    url:        "https://...s3.../files/product.jpg",
    bucketName: "my-bucket",
    filePath:   "EditedFiles/product.jpeg",
    prompt:     "prompts/{job_id}-front.json",
    width:      2116,
    height:     2700,
    colour_match: true
  }

  → Background removal: POST http://77.68.113.204:4000/api/image/upload-url-v4
  → request.url rewritten: "files" → "EditedFiles", extension → ".jpeg"
  → S3.get_object: prompts/{job_id}-front.json → enhance profile
  → fal_client.submit_async("fal-ai/flux-pro/kontext", {prompt, loras?, ...})
  → handler.get() → result image URL
  → colour_match_bytes(original, result) [if colour_match=True]
  → PIL resize to 2116×2700
  → S3.upload_fileobj: EditedFiles/product.jpeg
  ← Returns: {result_url: "https://...s3.../EditedFiles/product.jpeg", ...}
```

---

### Flow 2: Priority Job Processing

```
Step 1 — Client marks a job as priority
  POST /garment-tagging/upload → gets job_id
  GET /garment-tagging/priority?uuid=<job_id>  ← marks job priority=true in DynamoDB
  
Step 2 — Worker sees it in next scan cycle
  worker.py infinite loop → DynamoDB.scan (state=pending AND priority=true)
  → DynamoDB.update_item state=queued (conditional, race-safe)
  → SQS.send_message to PRIORITY_QUEUE_URL (bypasses normal queue)
  
Step 3 — Worker checks priority queue first each iteration
  SQS.receive_message from PRIORITY_QUEUE_URL
  → Submits to ThreadPoolExecutor first
  → Skips normal queue for this iteration
  
Result: Priority jobs cut the queue and are processed before all pending normal jobs
```

### AI Pipeline Decisions and Tradeoffs

**Why two Gemini passes instead of one?**\
The second pass uses dynamically selected allowed-value lists that depend on the eBay category determined in pass 1. If this were done in one pass, the prompt would need to include all possible valid values for every category (\~3,000+ values), which would overload Gemini's context window and reduce accuracy.

**Why Gemini for tagging, not OpenAI?**\
README notes this was migrated from OpenAI to Gemini. Multiple API keys support rate-limit distribution. Gemini's JSON output mode (`response_mime_type="application/json"`) with `temperature=0` gives highly consistent structured outputs.

**Why fal.ai for enhancement, not direct Stable Diffusion?**\
fal.ai provides managed GPU inference, eliminating the need to host GPU infrastructure. The `fal_client` SDK provides async submission with result polling. Multiple model variants (kontext, FLUX-2, LoRA, etc.) are all available through a unified API surface.

**Why LoRA for some enhancements?**\
LoRA (Low-Rank Adaptation) files fine-tune a base diffusion model for specific garment types. The `mh-flatlay` LoRA trains the model to correctly lay items flat. Category-specific LoRAs (mh-tops, mh-bottoms, etc.) train it for specific garment silhouettes. Stacking them gives better results for category-specific enhancement.

## 8. Shared Contracts and Parameters

### The Enhance Profile (Shared S3 Contract)

This JSON structure is the **primary shared contract** between AI-Tagging (writer) and AI-Image-Enhancer (reader):

```json
{
  "prompt": "Lay this navy slim-fit T-shirt perfectly flat...",
  "lora_prompt": "mh-flatlay mh-tops Lay this navy slim-fit T-shirt...",
  "guidance_scale": 3.0,
  "guidance_scale_lora": 3.2,
  "loras": [
    {
      "url": "https://s3.eu-west-2.amazonaws.com/...mh-flatlay.safetensors",
      "scale": 0.3
    },
    {
      "url": "https://s3.eu-west-2.amazonaws.com/...mh-tops.safetensors",
      "scale": 0.3
    }
  ],
  "metadata": {
    "uuid": "job-abc123",
    "image_url": "https://...",
    "orientation": "front",
    "garment_description": "Slim-fit cotton crew-neck T-shirt..."
  }
}
```

**S3 location convention:**

- Written by: AI-Tagging worker (`worker.py` via `build_enhance_profile`)

- Read by: AI-Image-Enhancer (`app.py` → `get_enhance_profile`)

- Key pattern: `prompts/{job_id}-{orientation}.json` where `orientation` is `"front"` or `"back"`

**Breaking this contract = silent failure.** If AI-Tagging writes a malformed profile, AI-Image-Enhancer will fail with an S3 or JSON parse error (HTTP 400). There is no validation of the profile structure on either side.

---

### Key Shared Parameters

| Parameter            | Defined In                 | Written By             | Read By                           | Type         | Notes                                              |
| -------------------- | -------------------------- | ---------------------- | --------------------------------- | ------------ | -------------------------------------------------- |
| `job_id` / `uuid`    | Client                     | Client                 | All services                      | `str`        | Cross-service correlation ID                       |
| `image_url`          | Client → AI-Tagging        | Client                 | AI-Tagging worker                 | `List[str]`  | Array; order matters (first=front, last=label)     |
| `ebay_category`      | prompting.py               | Gemini (Pass 1)        | enhance\_profile.py, prompting.py | `str`        | Controls LoRA selection and allowed value lists    |
| `fabric_type`        | Gemini output              | Gemini (Pass 2)        | enhance\_profile.py, Prompt-Gen   | `str`        | Controls guidance scale and denim special handling |
| `orientation`        | Hardcoded "front"/"back"   | AI-Tagging worker      | Prompt-Gen, enhance\_profile.py   | `str`        | Controls back-view stripping in Prompt-Gen         |
| `prompt` (S3 key)    | AI-Image-Enhancer request  | Client                 | AI-Image-Enhancer                 | `str`        | Must match S3 key written by AI-Tagging            |
| `loras` (in profile) | enhance\_profile.py        | AI-Tagging worker → S3 | AI-Image-Enhancer                 | `List[dict]` | `{url, scale}` per LoRA                            |
| `guidance_scale`     | enhance\_profile.py config | AI-Tagging worker      | AI-Image-Enhancer                 | `float`      | Could be 3.0 (default) or 2.5 (denim)              |

### Gemini Output → Enhance Profile Field Mapping

```
Gemini Pass 2 output:
  "ebay Category": "T-Shirts"
```

## 10. Failure Points and Recovery Paths

### Failure Point Map

| Component                  | Failure Mode                   | Impact                                                        | Current Recovery                                                           | Recommended                                                |
| -------------------------- | ------------------------------ | ------------------------------------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **AWS SQS**                | Service unavailable            | New jobs not queued; upload returns 500. Worker can't consume | Job marked error in DynamoDB                                               | Retry with backoff on SQS send; circuit breaker            |
| **AWS DynamoDB**           | Service unavailable            | Status queries return 500; state updates fail                 | One retry on upload put\_item; none on updates                             | Add DynamoDB error handling in worker with retry           |
| **Google Gemini API**      | Rate limit (429)               | Processing delayed                                            | Key rotation + exponential backoff (implemented)                           | Add alert when all keys exhausted                          |
| **Google Gemini API**      | Model unavailable (503)        | Processing delayed                                            | Exponential backoff retry (implemented)                                    | Monitor retry frequency                                    |
| **Prompt-Gen API**         | Service down                   | Enhance profiles not generated                                | Exception caught → logged as warning → job still completes without profile | Alert on enhance profile failure; consider making it fatal |
| **Prompt-Gen API**         | Timeout                        | Same as above                                                 | 30s timeout → exception caught                                             | —                                                          |
| **OpenAI API**             | Service unavailable            | Prompt generation fails                                       | Bubbles up as HTTP 500 from Prompt-Gen to AI-Tagging                       | Retry in `build_enhance_profile()`                         |
| **Background Removal API** | Service down                   | All 5 enhancement endpoints return 500                        | None — raises immediately                                                  | Circuit breaker; fallback to proceeding without removal    |
| **fal.ai API**             | Service down                   | Enhancement requests return 500                               | None                                                                       | Retry with backoff                                         |
| **fal.ai API**             | Slow response                  | Enhancement request hangs                                     | None — no timeout on `handler.get()`                                       | `asyncio.wait_for()` with timeout                          |
| **S3**                     | Write failure                  | Enhancement result lost                                       | `HTTPException(500)` with no retry                                         | Retry on S3 upload                                         |
| **S3**                     | Read failure (enhance profile) | Enhancement returns 400                                       | None                                                                       | Display helpful error, prompt to re-run tagging            |

### State Machine for Jobs (AI-Tagging)

```
                    ┌─────┐
                    │     │ POST /upload
                    ▼     │
              ┌─────────────┐      DynamoDB.scan + priority=true
              │   pending   │─────────────────────────────────► resent to PRIORITY queue
              └─────────────┘
                    │
                    │ SQS message sent at upload time
                    │ OR worker picks up from normal queue
                    ▼
              ┌─────────────┐
              │   queued    │   (conditional update — prevents race condition)
              └─────────────┘
                    │
                    │ Worker picks up from SQS (Priority or Normal)
                    ▼
              ┌─────────────┐
              │ processing  │
              └─────────────┘
                    │
         ┌──────────┴──────────┐
         │                     │
         ▼                     ▼
   ┌──────────┐           ┌──────────┐
   │ complete │           │  error   │
   └──────────┘           └──────────┘
```

**No state for "enhance profile writing failed"** — this is silently folded into `complete`. Jobs that complete without an enhance profile cannot be distinguished from jobs that succeed fully.

### Failure Propagation

```
Gemini API failure 
  → AI-Tagging Worker retry (with backoff + key rotation)
  → After all retries exhausted: job state = error in DynamoDB
  → Enhance profile NOT written to S3
  → AI-Image-Enhancer: if called with prompts/{job_id}-front.json → S3 get_object fails → HTTP 400

Prompt-Gen failure
  → AI-Tagging Worker: exception CAUGHT, logs warning
  → Job still completes with state=complete in DynamoDB
  → Enhance profile NOT written to S3  
  → AI-Image-Enhancer: if called with prompts/{job_id}-front.json → S3 get_object fails → HTTP 400
  → Client sees: tagging succeeded, enhancement fails with 400 and no explanation

Background Removal failure
  → AI-Image-Enhancer: raises HTTP 500 immediately
  → No enhancement performed
  → No S3 write
  → Client must retry entire enhancement request

fal.ai failure
  → AI-Image-Enhancer: raises HTTP 500
  → Same as above
```

## 11. Security and Validation Review

### Authentication Summary

| Endpoint                        | Auth               | Notes                                           |
| ------------------------------- | ------------------ | ----------------------------------------------- |
| `POST /garment-tagging/upload`  | **None**           | Any caller can submit jobs                      |
| `GET /garment-tagging/query`    | **None**           | Any caller can query any job by UUID            |
| `GET /garment-tagging/priority` | **None**           | Any caller can escalate any job                 |
| `POST /generate-prompt`         | `X-API-Key` header | Correctly implemented; key from env var         |
| `GET /health` (Prompt-Gen)      | None               | Standard for health endpoints                   |
| `POST /image-enhance/v1/*`      | **None**           | Any caller can trigger paid fal.ai jobs         |
| `GET, DELETE /cache/prompts`    | **None**           | Any caller can read or destroy the prompt cache |

**Most critical gap:** The `DELETE /cache/prompts` endpoint has no authentication. Any client on the network can wipe the prompt cache, causing all subsequent requests to re-fetch from S3 (performance impact + increased S3 costs).

**Second critical gap:** The enhancement endpoints call fal.ai (a paid service) with no auth. Any caller with network access to port 9090 can trigger billable AI jobs.

### Input Validation Gaps

| Service           | Field                | Issue                                                                                                               |
| ----------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------- |
| AI-Tagging        | `uuid`               | Not checked for uniqueness; duplicates silently overwrite DynamoDB records                                          |
| AI-Tagging        | `image_url` items    | Not validated as valid URLs (only MIME type guess from path)                                                        |
| AI-Tagging        | `attribute.category` | Not validated against `CONDITIONAL_VALUES["category"]` at API layer (only in worker later)                          |
| Prompt-Gen        | `orientation`        | Any string accepted; only `"front"` and `"back"` are meaningful                                                     |
| Prompt-Gen        | `item_type`          | Unsanitized; injected into LLM prompt directly (prompt injection risk)                                              |
| AI-Image-Enhancer | `url`                | Not validated as valid URL; `data:` URI accepted without content type validation                                    |
| AI-Image-Enhancer | `bucketName`         | Not validated; arbitrary S3 bucket name accepted — could be used to read from any bucket the IAM role has access to |
| AI-Image-Enhancer | `filePath`           | Not validated; S3 path traversal not possible in S3, but unexpected key structures could occur                      |

### Credential Management Issues

| Issue                                                    | Location                   | Risk                                                                              |
| -------------------------------------------------------- | -------------------------- | --------------------------------------------------------------------------------- |
| `AWS_SECRECT_KEY` typo in env var name                   | `main_api.py`, `worker.py` | Must be typo'd in `.env` — invisible bug                                          |
| Mixed credential strategies (env vars vs named profiles) | All files                  | SQS uses env vars; DynamoDB uses named profile — inconsistent, breaks differently |
| LoRA S3 URLs hardcoded (non-configurable)                | `enhance_profile.py`       | S3 bucket/key changes require code changes                                        |

- AI-Tagging → Prompt-Gen: HTTP (protocol not specified, assumed HTTP internally) \[Needs Verification]

- AI-Image-Enhancer → Background Removal: Explicitly `http://` (no TLS) — sensitive image URLs transmitted unencrypted

## 12. Performance and Scalability Notes

### Latency Profile Per Service

| Service                     | Bottleneck                        | Typical Latency |
| --------------------------- | --------------------------------- | --------------- |
| AI-Tagging API              | DynamoDB write + SQS send         | \< 500ms        |
| AI-Tagging Worker (per job) | Gemini 2 passes + image downloads | 5–30 seconds    |
| Prompt-Gen                  | LLM inference: 4–10s              | 4–10 seconds    |
| AI-Image-Enhancer           | fal.ai inference                  | 15–60 seconds   |

### Concurrency Models

**AI-Tagging Worker:**

- `ThreadPoolExecutor(max_workers=len(GEMINI_KEYS))`

- Parallelism limited to number of API keys

- Each thread processes one job at a time (download frames → Gemini 2 passes → S3 write)

- Adding more Gemini keys directly increases throughput

**AI-Image-Enhancer:**

- FastAPI handles requests with `async def` handlers

- Multiple enhancement requests can be in-flight simultaneously (async I/O)

- Actual fal.ai inference is serialized per request but Python doesn't block during `await handler.get()`

- FastAPI + uvicorn default worker count applies

**Prompt-Gen:**

- FastAPI with sync handlers (`def generate_prompt`, not `async def`)

- Under high concurrency, sync handlers may block uvicorn workers

- Recommended: run with multiple uvicorn workers or use `async def` with `asyncio.to_thread` for blocking LLM calls \[Needs Verification: some OpenAI SDK calls may be synchronous]

### Known Performance Bottlenecks

1. **DynamoDB full-table scan per worker loop iteration** — `O(n)` where n = number of all jobs ever processed. Grows unboundedly without TTL.

2. **`prompt_cache`****&#x20;in AI-Image-Enhancer** — unbounded growth. In a long-running process processing many unique prompts, memory usage grows indefinitely.

3. **AI-Image-Enhancer synchronous S3 read on every enhancement request** — enhance profiles are not cached. If the same profile is used for 100 images (common batch scenario), S3 is read 100 times. \[Inconsistency: `.txt` prompts ARE cached, but S3 `.json` enhance profiles are NOT]

4. **Sequential Prompt-Gen calls for front and back** — `build_enhance_profile` is called twice sequentially in the worker. These could be parallelized with `asyncio.gather` or `concurrent.futures`.

5. **Image grid saved to disk then reloaded** — `make_image_grid()` saves to a temp file then the file is read back as PIL Image. This is disk I/O that could be eliminated by keeping the PIL Image in memory.

### Scaling Characteristics

| Scale Factor              | Effect                                                                                         |
| ------------------------- | ---------------------------------------------------------------------------------------------- |
| More concurrent clients   | AI-Tagging API scales horizontally; SQS and DynamoDB are managed services with high throughput |
| More jobs in queue        | Worker throughput is bounded by `len(GEMINI_KEYS)`                                             |
| More Gemini keys          | Linear throughput increase in worker                                                           |
| Larger DynamoDB table     | Linear increase in scan cost — must add GSI                                                    |
| More enhancement requests | AI-Image-Enhancer scales horizontally; fal.ai handles GPU concurrency                          |

## 15. Suggested Improvements

### High Priority (Fix Before Production)

1. **Fix SyntaxError in&#x20;****`AI-Image-Enhancer/app.py`** — the `enhance_image_by_gemine_nano_banana` function has a malformed f-string comment that prevents the module from loading

2. **Add authentication to AI-Tagging and AI-Image-Enhancer** — at minimum, shared API key checking. Without this, anyone on the network can trigger paid AI jobs and read/modify job data

3. **Move ALL hardcoded values to env vars:**

   - `AWS_SECRECT_KEY` → fix typo to `AWS_SECRET_KEY`

   - `http://77.68.113.204:4000` → `BACKGROUND_REMOVAL_URL`

   - `IS_BACKGROUND_REMOVAL = True` → `BACKGROUND_REMOVAL_ENABLED` env var

   - `BACKGROUND_TEMP_BUCKET = "test-rishvi"` → env var

   - LoRA `.safetensors` S3 URLs in `enhance_profile.py`

4. **Add DynamoDB TTL** — configure a TTL field to auto-expire completed jobs, preventing unbounded table growth and improving scan performance

5. **Replace DynamoDB scan with GSI** — create a Global Secondary Index on `{priority, state}` so the worker can query instead of scan

### Medium Priority (Before Scaling)

1. **Add timeout to all outbound HTTP calls:**

   - `requests.post()` in background removal: add `timeout=30`

   - `httpx.get()` in Prompt-Gen: add `timeout=30`

   - `handler.get()` in fal.ai calls: wrap with `asyncio.wait_for(..., timeout=120.0)`

2. **Add distributed tracing / correlation ID** — forward `job_id` as `X-Request-ID` header in all inter-service HTTP calls; include it in all log lines

3. **Cache enhance profiles (****`.json`****) in AI-Image-Enhancer** — currently `.txt` prompts are cached but `.json` profiles are not. For batch processing, this means N S3 reads for N images of the same garment.

4. **Parallelize front and back Prompt-Gen calls** — `build_enhance_profile` is called twice sequentially in `process_job`. Use `asyncio.gather` or `concurrent.futures.ThreadPoolExecutor` for both calls simultaneously.

5. **Add structured logging across all services** — use a JSON log format with: `timestamp`, `service`, `job_id`, `operation`, `duration_ms`, `status`. This enables log aggregation.

6. **Create systemd units for Prompt-Gen and AI-Image-Enhancer** — currently only AI-Tagging has systemd service definitions.

### Architecture Improvements

1. **Consider event-driven decoupling for AI-Image-Enhancer** — currently a client must call AI-Image-Enhancer separately after AI-Tagging completes. An alternative: have the AI-Tagging worker publish a completion event to SQS/SNS that triggers enhancement automatically. This would make the pipeline fully automated end-to-end.

2. **Add schema versioning to the enhance profile** — add a `version` field to the S3 JSON. This allows AI-Image-Enhancer to handle profile format changes gracefully without breaking existing profiles.

3. **Validate the enhance profile at write time** — AI-Tagging should validate the profile JSON before writing to S3, not silently write malformed data that failures silently in AI-Image-Enhancer.

4. **Circuit breaker on background removal dependency** — implement a simple circuit breaker in AI-Image-Enhancer. If background removal fails N times in a row, stop calling it for T seconds (open circuit). This prevents cascading failures when the background removal service is down.
